Architecture

The Architecture Diagram shows the high-level design of GameMates. The following sections describe the main components and their interactions.

Application startup and shutdown

The Main component controls application startup and shutdown. It consists of Main and MainApp.

  • At startup, this component initializes the other components in the necessary sequence and connects them.
  • At shutdown, it stops the other components and calls cleanup methods where necessary.

Main components

Four components do most of the application’s work:

  • UI provides the user interface.
  • Logic executes commands.
  • Model holds the application data in memory.
  • Storage reads data from the hard disk and writes data to it.

Commons contains classes that more than one component uses.

UI component

The component API is defined in Ui.java.

UI classes and layouts

The UI consists of these classes, which inherit from UiPart:

  • MainWindow
  • CommandBox
  • ResultDisplay
  • FriendListPanel
  • FriendDetailsPanel
  • GameDetailsCard
  • HelpWindow
  • StatusBarFooter

UiPart loads the matching FXML layouts. TagPane and TagLabel wrap tags to the available width in friend cards and the details panel. TagPane measures wrapped labels before layout and constrains their width during layout. TagLabel adjusts its height to keep wrapped text visible.

MainWindow.fxml uses a SplitPane. The observable friend list is on the left, and the details panel is on the right. FriendDetailsPanel shows contact details, tags and sorted game cards. It does not replace the friend list.

The UI uses the JavaFX framework. Its .fxml layout files are in src/main/resources/view. For example, MainWindow.fxml defines the layout of MainWindow.

Component responsibilities

The UI component:

  • Executes user commands through Logic and keeps a reference to that component.
  • Listens for changes to Model data so that the display can show those changes.
  • Depends on model classes because it displays Friend objects.

Selection and command results

FriendListPanel sends selection changes to a consumer in MainWindow. Command-driven selection uses CommandResult.friendToShow, showMyself and gameFilter. See Viewing games.

If a successful result has no friend payload, the details panel shows Logic.getMyself(). If find returns one friend, the details panel shows that friend. Parse failures and command failures update feedback without an explicit details refresh.

MainWindow.refreshFriendDetails calls FriendListPanel.selectFriend() before it sets the final details payload. Friend payloads select the matching displayed friend; profile payloads and results without a friend clear the selection. If the target is not displayed, selectFriend() also clears the selection. Mouse selection remains supported, and a previous friend can be selected again after a command shows the profile.

A game filter changes only the cards that the panel renders. The filter does not change the model or the predicate for the left-hand friend list.

Command execution

LogicManager.execute(commandText) follows this sequence:

  1. LogicManager passes the command text to a GameMatesParser object. This object creates a matching parser instance, such as a DeleteCommandParser, and uses it to parse the command.
  2. The parser creates an instance of a Command subclass, such as DeleteCommand. LogicManager executes that command object.
  3. The command communicates with Model as necessary, for example to delete a friend. The diagram shows one interaction for simplicity. The code can use more than one interaction to complete the operation.
  4. The command creates a CommandResult. LogicManager obtains the data through Model.getGameMates(). Before it returns the result to the UI, LogicManager saves the complete ReadOnlyGameMates through Storage.

Viewing commands also save data. Parse failures and execution failures skip the save. If an I/O error occurs after execution, LogicManager reports a CommandException. It does not roll back the change in memory.

Command parsing

The following diagram shows the parsing classes omitted from the class diagram above.

GameMatesParser creates an instance of an XYZCommandParser, where XYZ represents the command name. Each parser uses the shared parsing classes to create an instance of its XYZCommand class. For example, AddCommandParser creates an AddCommand object. GameMatesParser returns the result as a Command object.

All command parsers implement the Parser interface, including AddCommandParser and DeleteCommandParser. This interface lets callers use the parsers in the same way, for example in tests.

Optional values

Command parsers and edit descriptors use Vavr Option to represent omitted values. A missing prefix is absent. A prefix with an empty value is present and must pass validation.

Add commands use Phone.EMPTY and Email.EMPTY for omitted contact details. Edits preserve omitted fields. A single empty t/ clears the tags. Descriptor setters make defensive copies of tag sets, and their getters return unmodifiable sets.

Parsing reports the first invalid value through ParseException. Vavr’s checked-function adapters propagate the original exception. Thus, an invalid value is not treated as an omitted argument.

GameAddCommandParser uses Username.EMPTY when u/ is omitted. It rejects a supplied blank u/.

Quoted values

ArgumentTokenizer lets users wrap a whole value in double quotes. Prefixes inside the quotes are literal text, so g/"PUBG n/Game" gives PUBG n/Game.

  • A value is quoted when its first character after trimming is ". Its content is trimmed like any value.
  • In any value, \" is a literal ". Only the backslash right before a quote is removed, so \\" gives \".
  • A quoted value cannot end with \ right before the closing quote, since \" is read as a literal ". Users add a space before the closing quote instead, which trimming removes.
  • A bare " in an unquoted value, a missing closing quote or text after the closing quote throws a ParseException. Each case has its own message.
  • Only straight quotes " are supported. Other quotes such as curly quotes “ ” do not start or end a quoted value. They are kept as normal text.
  • The preamble is not parsed for quotes.

Model component

API: Model.java

Stored data and views

The Model stores friends in GameMates through UniqueFriendList. It stores a separate Friend myself profile with a default value. The profile is not part of the friend list. Add and edit commands prevent a friend and the profile from sharing a name.

A FilteredList<Friend> provides an observable view of the stored friends. Its predicate operates on the full collection; the filter does not create a second collection of copied friends. FriendListScope identifies active, archived and global search views, including empty results. ModelManager exposes a SortedList over this filtered list to apply the display order.

Each friend’s games are Game objects. Each object contains a game name, an optional username and optional metadata. The Model also stores a UserPrefs object, which currently holds GUI settings. Other components read these preferences through ReadOnlyUserPrefs.

Model does not depend on UI, Logic or Storage. Its classes represent domain data and make sense without those other components.

Friend fields and pin order

Friend contains a Name, optional contact values, a set of Tag objects and a set of Game objects. It also contains immutable archived and pinned states. See Friend archiving for the scope, identity and persistence rules.

UniqueFriendList.MAX_PINNED_FRIENDS limits the stored collection to five pins across active and archived friends. The list validates this invariant on addition, replacement and bulk replacement. A violation throws PinnedFriendLimitExceededException before the collection changes. Tag names contain 1–50 ASCII alphanumeric characters.

After additions and replacements, UniqueFriendList stably partitions friends, with pinned friends before unpinned friends. It preserves the existing relative order within each group. Filters use that stored order, so filtering preserves this invariant. An explicit sort uses a separate display comparator and can override the pin order in the current implementation.

Game fields and identity

Game contains a GameName, a Username and an immutable metadata set. Name equality ignores case and treats repeated ASCII spaces as one space. GameName.equals compares complete names after lower-case normalization with Locale.ROOT.

Username preserves case. An omitted username uses Username.EMPTY; isEmpty() identifies that value. Game.isSameGame compares game names. Full game equality also compares usernames and metadata.

GameValidator rejects an existing game name during addition or renaming, regardless of its username. Full game equality alone does not enforce this rule, so JsonAdaptedFriend also validates game-name uniqueness during loading. Duplicate names reject the load even when usernames differ.

Alternative model design: An alternative, arguably more object-oriented design keeps a unique tag list in GameMates. Each Friend references tags in that list. This lets GameMates keep one Tag object per unique tag, instead of separate tag objects in each friend. The diagram below shows this alternative.

Storage component

API: Storage.java

Storage classes

Storage saves GameMates data and user preferences in JSON files. It reads those files back into the corresponding objects. StorageManager delegates file access to JsonGameMatesStorage and JsonUserPrefsStorage, with one class per data file. Storage depends on model classes because it saves and restores model objects.

JsonAdaptedGame and JsonAdaptedMeta convert game metadata. They validate fields and reject duplicate metadata keys during the load. JsonSerializableGameMates adapts friends and myself. JsonAdaptedFriend adapts games and tags. JsonAdaptedGame adapts name, username and metas.

Read results and startup defaults

Storage reads return Vavr Option. A missing file produces an absent value. Malformed JSON or invalid stored friend data causes DataLoadingException. Vavr Try captures JSON read failures and model-conversion failures. It converts them to checked DataLoadingException instances and keeps the original cause.

If the GameMates file is missing, startup uses sample data. If a load error occurs, startup uses an empty GameMates. Missing or unreadable preferences use the default preferences.

Defaults and validation in stored data

Null or empty contact fields become the corresponding empty contact values. Invalid non-empty contacts are rejected without trimming. Missing or null games and tags load as empty sets. Missing myself uses Friend.DEFAULT_MYSELF.

Stored games must have a valid name. Missing, null or empty usernames become Username.EMPTY. Invalid non-empty usernames, including whitespace-only strings, are rejected.

Duplicate friend names reject the entire load, including a profile parsed before the duplicate was found. Startup then uses a new empty GameMates. JsonAdaptedFriend saves the pinned boolean. Missing or null pin values in older files default to false.

JsonAdaptedFriend rejects duplicate GameName values within either a friend or the profile. JsonSerializableGameMates rejects friend names that match the profile and converts excess pins to IllegalValueException. These failures reject the entire load, not only the invalid entry. The untouched Friend.DEFAULT_MYSELF uses Name.EMPTY and is omitted from saved JSON. Stored friend/profile entries still need valid non-empty names.

File paths and save timing

MainApp resolves data/gamemates.json and preferences.json relative to the process working directory, not the JAR location. MainApp.initPrefs writes initialized preferences at startup. stop writes them again at shutdown. Before shutdown, MainWindow.handleExit records the current window dimensions and position.

Commands save the data model; stop does not save it. Selection, view scope, sorting and filter predicates are transient and are not saved.

Unknown fields and damaged files

Jackson ignores unknown JSON properties. Those properties disappear the next time the data is serialized. The loader does not repair or back up damaged files. The next successful command can overwrite a damaged file with fallback data. There is no automatic recovery or atomic transaction across command execution and file writing.

Null JSON and GUI preferences

JsonUtil.readJsonFile calls requireNonNull on the deserialized root inside Try. A null root causes a NullPointerException that is converted to DataLoadingException. A data file containing only null therefore uses the usual empty-data fallback. UserPrefs.setGuiSettings() has @JsonSetter("guiSettings") and rejects an explicit null value during deserialization. MainApp.initPrefs catches these preference-load failures and uses and saves default preferences. Null window coordinates remain valid; they do not mean that the entire guiSettings object is null.

Common classes

Implementation

This section describes some noteworthy details on how certain features are implemented.

Friend creation, editing and deletion

Adding a friend

AddCommandParser accepts a command only if n/ is present. It uses Phone.EMPTY and Email.EMPTY for omitted contact values. ParserUtil trims supplied values before it calls the model validators.

ArgumentMultimap rejects duplicate single-value name and contact prefixes. It collects repeated tags into a set. UniqueFriendList rejects names that are equal under Friend.isSameFriend. Different phone numbers, email addresses or tags do not distinguish duplicate names.

Editing a friend or profile

EditCommandParser accepts a numeric index or the case-insensitive myself keyword. It rejects an omitted selector. Target resolution and replacement use the Myself profile mechanism. Add and edit commands reject names shared between a friend and the profile.

EditFriendDescriptor uses optional values to distinguish an omitted field from an empty contact field. EditCommand creates a replacement friend and preserves the original games. Supplied name and contact values replace their existing values. An empty p/ or e/ clears that contact value during an edit. Add commands reject these empty prefixes.

Supplied tags toggle according to set membership. A duplicate tag in one command applies only once. A single empty t/ clears all tags. Empty and non-empty tag parameters together fail validation.

Effect on the displayed list

Adding a friend switches to the unfiltered active view. Editing a displayed friend clears the filter in active and archive views, but preserves a global name-search predicate. If a renamed friend no longer matches the name predicate, that friend can disappear from the results. Editing Myself preserves the current scope and predicate, including an empty displayed list.

Deletion and clearing

DeleteCommand uses the same displayed-list indexing and keeps the current predicate. It immediately removes the entire friend and their games. There is no confirmation state.

An empty list or out-of-range index produces the shared generic deletion error. In contrast, EditCommand and GameListCommand distinguish empty lists and report a displayed range. ClearCommand replaces the friends with an empty GameMates and copies the existing profile.

Field validation

The contact rules differ from the submitted draft. Names accept 1–100 ASCII alphanumeric characters and spaces. Phone validation examines digit counts and grouping. Email validation uses ASCII dot-atom and domain syntax with length limits. The User Guide defines the accepted input.

No phone number, email address, game name or username is verified against an external service. GameName and Username use String.strip() to trim values. The values must contain a letter or digit. Length is counted in UTF-16 units with String.length(). The shared text validator rejects:

  • Unicode category C: controls, format characters, unpaired surrogates, private-use and unassigned characters
  • line (Zl) and paragraph (Zp) separators
  • characters that render blank: Hangul fillers U+115F, U+1160, U+3164 and U+FFA0, blank Braille U+2800 and the combining grapheme joiner U+034F
  • no-break spaces U+00A0, U+2007 and U+202F, which look like regular spaces but do not match them

Other Unicode is accepted, including combining marks, emoji and variation selectors. These rules define the application’s accepted text characters; they do not test how every font renders each character.

Myself profile

GameMates stores the user’s profile as a separate Friend, initially Friend.DEFAULT_MYSELF. edit, gameadd and gamedel accept myself independently of the displayed friend list and profile name. The default profile has Name.EMPTY, rather than reserving the friend name Myself. The first edit myself must supply a name, as in edit myself n/NAME. Later profile edits can omit it.

Their syntax uses FRIEND_INDEX|myself. This selector accepts either a positive displayed friend index or the case-insensitive profile keyword:

edit FRIEND_INDEX|myself [n/NAME] [p/[PHONE_NUMBER]] [e/[EMAIL]] [t/TAG]…
gameadd FRIEND_INDEX|myself g/GAME_NAME [u/USER_NAME] [m/KEY:VALUE]…
gamedel FRIEND_INDEX|myself g/GAME_NAME
gameedit FRIEND_INDEX|myself g/EXISTING_GAME [n/NEW_GAME_NAME] [u/USERNAME] [m/KEY:VALUE]…
gamelist FRIEND_INDEX|myself [g/GAME_NAME]

Target resolution

The sealed FriendTarget interface lets these commands update the profile or a listed friend. Its nested Myself and ListedFriend records retain the selected Friend and identify the update destination. They keep that destination even if the friend-list filter changes.

The class diagram omits unrelated members. It shows the records as ordinary classes.

  1. The three command parsers use ParserUtil.parseIndexOrMyself. A case-insensitive Index.MYSELF_KEYWORD becomes Index.myself(); numeric selectors remain displayed friend indices.
  2. During execution, ModelManager.resolveFriend(index) captures the profile or currently displayed friend in a target.
  3. The command constructs and validates a replacement Friend, then calls ModelManager.setFriend(target, updatedFriend). An exhaustive switch routes Myself to the profile and ListedFriend to its captured friend.

Validation and saving

For profile edits, EditCommand constructs the replacement before FriendValidator examines name conflicts. Validation uses all stored friends, including friends hidden by the current filter. Profile edits and both game commands preserve the friend-list filter. FriendValidator.checkFriendInitialized() rejects gameadd, gameedit, gamedel and gamelist for an unnamed profile. The feedback is Set your profile name first using "edit myself n/NAME" command.

The following sequence shows gameadd myself g/Valorant u/player after parsing. It omits helper calls and the subsequent save.

After success, LogicManager saves friends and myself through JsonSerializableGameMates. MainWindow refreshes the profile through Logic.getMyself(). If older JSON omits myself, the application keeps the default profile.

Name and game filtering

Filter predicates

FindCommand installs NameContainsKeywordsPredicate. A full name word matches if it equals any supplied keyword, ignoring case.

ListCommand installs either PREDICATE_SHOW_ALL_FRIENDS or GameNameMatchesPredicate. The game predicate matches if any game belonging to a friend has the exact GameName. find searches all stored friends; list selects active friends from the stored collection. Both commands replace the previous predicate. Their filters do not intersect.

Display order

After filtering, list s/name and list s/game set a SortedList comparator in ModelManager. The default direction and o/asc use ascending order. o/desc reverses the comparator. The default list clears the comparator and keeps the stored insertion order.

Game sorting uses each friend’s alphabetically first game name. Friend names resolve ties. Ascending game order puts friends without games last. Reversing the comparator currently also reverses that placement.

Parser behavior and empty results

find does not parse prefixes, and list does not parse n/. The find parser accepts a non-empty keyword list; it does not enforce a 255-character keyword limit. Queries with no matches return successful empty results. Filtering and sorting never include or edit the separate profile.

Editing an existing game

Parser and field values

GameEditCommandParser reuses ArgumentTokenizer, ArgumentMultimap, ParserUtil.parseIndexOrMyself, parseGameName, parseUsername and parseMetas. Its immutable EditGameDescriptor distinguishes omitted metadata (null) from an empty replacement set. The descriptor copies supplied metadata. At least one editable field must be supplied.

A single empty m/ clears metadata. All other supplied pairs pass through the shared parser, including normalized duplicate-key validation and first-colon splitting. The model identity rules do not change.

The merged optional-username model provides Username.EMPTY. A supplied empty u/ maps to that value. If u/ is omitted, the command preserves the original username, including an absent username.

Quoted field values use the shared ArgumentTokenizer behavior described in Quoted values.

Validation before mutation

GameEditCommand uses FriendTargetResolver and Model.resolveFriend for displayed indices or Myself. GameTargetResolver.resolve() accepts exactly one matching existing game for gameedit and gamedel. The command constructs the complete replacement and examines name collisions against the other games. Only then does it call Model.setFriend(target, updated) once.

GameAddCommand delegates name-conflict validation to GameValidator.checkCanAdd(). GameEditCommand uses GameValidator.checkCanEdit() for the same validation during a rename. checkCanEdit() excludes the original game, so case-only renames remain valid. The resolver rejects missing games and defensively rejects ambiguous in-memory names without mutation. Externally edited JSON with duplicate game names is rejected during loading. Friend.withGames copies all current friend fields and makes a defensive copy of the replacement set. The copy preserves the original archive and pin statuses. Its explicit copy constructor must also copy new fields from future integrations.

View updates and persistence

The command retains the list predicate. A successful friend edit returns the updated friend through CommandResult and clears the previous game-card filter. A successful profile edit uses the existing profile refresh. Failures return no result and preserve the current details.

LogicManager saves through the existing storage path; this feature adds no persistence mechanism. There is no transaction across model mutation and a disk-write failure.

Test coverage

Tests cover pinned order and archived targets in archive and global search scopes. Save/reload tests verify both archive and pin status. Other tests cover command routing, atomic validation, displayed targets, metadata replacement and profile updates. They also cover case-only spelling, UI refresh and real JSON storage round trips.

Viewing a friend’s games

gamelist FRIEND_INDEX|myself [g/GAME_NAME] selects a friend or profile for the right-hand details panel. It does not change the left-hand friend list.

Parsing and target selection

GameMatesParser routes gamelist to GameListCommandParser. The parser accepts one positional index or myself before at most one g/ filter. It uses the shared ArgumentTokenizer, so all text after g/ belongs to the name unless it is another ` g/. Quoted values can include literal g/ text. Repeated g/` tokens outside quotes are rejected.

The parser uses ParserUtil.parseIndexOrMyself for selectors and the existing GameName rules for game validation. Index, repeated-prefix and game-name errors use the same shared messages as other commands.

GameListCommand.execute resolves numeric indices against Model.getFilteredFriendList(). This keeps indices consistent after name searches and game-based filtering. The command examines empty and out-of-range lists before numeric lookup. Model.resolveFriend resolves the selected friend or separate profile. myself works with an empty displayed list after profile setup; FriendValidator.checkFriendInitialized() rejects an unnamed profile.

GameName.equals gives exact, case-insensitive matching. No match and no games both return successful results.

Command result and feedback

CommandResult carries the original Friend in friendToShow and an optional GameName in gameFilter. The showMyself flag distinguishes the profile from a friend with identical details.

A filter must have a selected friend. The filter participates in equality, hashing and diagnostic output; existing constructors default to no filter. Matching feedback uses the stored game-name spelling. If no game matches, feedback uses the trimmed query.

Rendering and filter clearing

MainWindow.refreshFriendDetails passes the selected friend, profile flag and game filter to FriendDetailsPanel.setFriend. The panel filters the stream that constructs GameDetailsCard instances. If that stream has no entries, the panel shows an explicit empty label. It never constructs a replacement friend or modifies the original game set.

An unfiltered command clears the game filter. The existing two-argument setFriend also clears it, including when FriendListPanel reports another selection. A single-result find continues to select the whole friend. Parse failures and execution failures preserve the previous game display without a panel refresh. MainWindow also selects the displayed friend or clears the list selection for a profile result.

The command does not update the friend-list predicate, friends, games, preferences or Myself profile. The profile fallback still shows all profile games. Explicit profile selection supports game filtering after profile setup.

GameDetailsCard renders Game.getGameName(), Game.getUsername() and Game.getMetas(). Metadata pairs appear below the username as wrapping Key: Value labels, sorted by key ignoring case. The command’s original-friend payload retains metadata without copying or removing it.

Test coverage

Parser and command tests cover errors, exact matching, empty results, displayed-list indexing and unchanged model data. JavaFX panel and window tests cover filtered payloads, empty states, filter clearing through commands and selection. They also verify that invalid input preserves the details view.

Game metadata

Metadata records game-specific details, such as a friend’s role or play style. Meta, MetaKey and MetaValue are immutable classes in seedu.address.model.game.meta. Each Meta contains one key and one value.

Game copies the supplied metadata collection and returns an unmodifiable set through getMetas(). Its two-argument constructor uses an empty set.

Validation and equality

Before validation and storage, String.strip() removes leading and trailing whitespace. StringUtil.isValidTextField() accepts non-empty text with at least one letter or digit. It rejects the characters listed in Friend creation, editing and deletion. Limits use String.length(), which counts UTF-16 units. Supplementary characters count as two units.

The validation allows punctuation and permitted combining marks, emoji and variation selectors. It rejects Unicode format characters and the other categories listed in the shared rules above. GameName and Username use the same utility.

Field Length after trimming Colon handling Equality
MetaKey 1–50 Colons rejected Case-insensitive using Locale.ROOT
MetaValue 1–200 Colons allowed Case-sensitive

Keys must be unique within each game entry, even if repeated pairs have identical values. The same key can occur in other games or friends. Game enforces this invariant during construction.

Meta.equals() compares both fields. Game.equals() includes metadata, but isSameGame() compares only the game name.

Parsing

ParserUtil.parseMeta() uses StringUtil.splitAtFirstColon(). It delegates field parsing to parseMetaKey() and parseMetaValue(). For example, ` Role : Support:Mid ` becomes key Role and value Support:Mid. Missing separators and invalid fields cause ParseException.

parseMetas() parses a collection of raw values. Before it returns a set, it rejects duplicate normalized keys. Callers must pass all raw values without removing duplicates first. This lets the parser reject identical repeated pairs too.

GameEditCommandParser uses these utilities for metadata replacement. It treats a single empty m/ as a request to clear metadata.

GameAddCommandParser tokenizes the optional, repeatable CliSyntax.PREFIX_META (m/) alongside g/ and u/. It passes all raw metadata values to parseMetas() and constructs the Game with the validated set. If m/ is omitted, the result is an empty set.

Duplicate g/ or u/ prefixes remain invalid. Repeated m/ prefixes are valid only for distinct keys. Validation finishes before the command updates either a friend or the profile.

Display

GameDetailsCard shows each metadata pair as a wrapping Key: Value label below the username. Pairs are sorted by key ignoring case. Their stored spelling and values do not change. If the metadata container is empty, it is hidden and unmanaged.

Friend details and profile details use these cards, including views with a game filter.

Persistence and testing

JsonAdaptedGame stores metadata as a metas array of JsonAdaptedMeta objects:

{
  "name": "Valorant",
  "username": "player",
  "metas": [{ "key": "Role", "value": "Support:Mid" }]
}

Missing or null metas fields load as an empty set. This preserves compatibility with existing save files. Null array entries, invalid fields and duplicate keys cause IllegalValueException during model conversion.

Tests cover trimmed length boundaries, Unicode, control characters, colons and case normalization. They also cover duplicate keys, immutability, JSON round trips and metadata preservation during contact edits.

Command tests cover optional and interleaved metadata flags, malformed input, and metadata addition to displayed friends and myself. These tests include filter preservation, duplicate-game rejection and JSON round trips.

GameBuilder.addMeta("Role", "Support") appends a pair. withMetas(...) replaces the collection. If the builder contains duplicate keys, build() rejects them.

Friend archiving

Archiving hides a friend from the active list. It preserves contact details, tags, games, optional usernames and game metadata. The implemented commands are archive FRIEND_INDEX, unarchive FRIEND_INDEX and archivelist [g/GAME_NAME].

This feature is separate from JSON file backups. Automatic backups, scheduled retention and undo are not implemented.

Stored status and identity

GameMates keeps active and archived friends together in one UniqueFriendList. Friend.isArchived() returns an immutable boolean. withArchived(boolean) returns a copy and preserves all other fields.

Friend.equals() and hashCode() include archive status. isSameFriend() continues to compare normalized names.

Names must be unique across active and archived friends together. They must also differ from the separately stored Myself profile. An archived friend’s name stays reserved.

FriendValidator rejects a conflicting add or rename. If the existing friend is archived, the feedback suggests archivelist and unarchive. The validator uses Model.findFriend() for one identity lookup across both statuses, independently of the display filter.

An existing friend can keep their own name during an edit. Myself cannot be archived or restored.

Display scope and filtering

ModelManager stores a FriendListScope independently of the displayed list contents:

Scope Entered by Predicate
ACTIVE Startup, list [g/GAME_NAME], adding a friend Not archived, combined with an optional game predicate
ARCHIVED archivelist [g/GAME_NAME] Archived, combined with an optional game predicate
SEARCH find KEYWORD [MORE_KEYWORDS] Name keywords across both statuses

ListCommandParser and ArchiveListCommandParser use GameNameMatchesPredicate for exact, case-insensitive game matching. Both commands use the same game-name validation rules. ArchiveListCommandParser uses ParserUtil.parseOptionalGameFilter(); the active-list parser also handles sorting. Name matching remains a global find operation.

Each list, archivelist or find command replaces the previous predicate. gamelist preserves the friend-list filter. An unfiltered empty archive gives guidance on archiving. An empty filtered archive reports that no archived friends match the game filter.

The logic layer exposes getFriendListScope() to the UI. MainWindow sets the heading to Active friends, Archived friends or Search results. FriendCard shows an Archived badge where applicable.

Archive and restore execution

  1. The parser accepts one positive displayed index. It rejects myself and extra arguments.
  2. ArchiveCommand rejects the archive-only scope and gives guidance to use list. Active lists and global search results accept archiving. UnarchiveCommand accepts an archived target in archive or search results.
  3. The command validates the index against the displayed list and examines the target’s archive status. It rejects an invalid index, an already archived archive target, or a non-archived restore target. Failed commands preserve the data, scope and filter.
  4. Model.setFriend() replaces the selected friend with a copy that has the new archive status.
  5. The observable filtered list updates automatically. Archiving removes the friend from an active-only list; restoring removes the friend from an archive-only list. In global search, the friend stays at the same displayed position with the new status. Neither command resets the predicate or scope.
  6. LogicManager saves the updated collection through the existing storage path.

edit, gameadd, gameedit and gamedel preserve archive status in replacement friends. gameedit also retains the current scope and predicate. Friend edits clear filters in active and archive scopes, but global searches keep their name predicate. Thus, a renamed search result can disappear from the results.

delete permanently removes the selected friend, whether active or archived. clear removes both statuses and preserves Myself.

Persistence and design considerations

JsonAdaptedFriend saves archived as a boolean on each friend. If an older file omits the status, the value defaults to false. A restart restores each friend’s status and details, but starts in the unfiltered active scope. Display scope and predicates are not persisted.

A single stored collection keeps identity validation, storage and archive/restore updates on the existing model path. The alternative uses separate stored collections for active and archived friends. That approach needs transfers, cross-list uniqueness validation and a different JSON representation.

Rebuilding a filtered view scans the underlying collection. Separate collections can reduce the scan for active-only views, but global name search must still examine both collections. The current design favors simpler state management. If measurements establish a performance need, change this design.

Regression tests cover mixed-status searches, filtered displayed indices, invalid targets and empty archive feedback. They also cover identity conflicts, edits to archived friends, and save/reload restoration of complete game data.

Non-Functional Requirements

These requirements are targets, not measured guarantees. Capacity and performance require separate validation.

Environment

  1. Should run offline on a single user’s personal laptop running a mainstream OS, requiring only Java 25 or above.
  2. Should display all panels and the command box without scrolling at the default window size on screens with a resolution of 1280 x 720 or higher.

Data

  1. Should store all data locally in human-editable JSON files and send no data over the network.
  2. Should save data after successful commands and window preferences on shutdown, restoring saved data on the next launch from the same working directory.
  3. Should start without crashing, using sample data if the data file is missing or an empty list if it is corrupted.

Capacity

  1. Should support up to 1000 friends in total across the active and archived lists, excluding the user profile, each with up to 100 game entries.

Performance

On a modern computer running Java 25, with up to 1000 friends in total across the active and archived lists, excluding the user profile, and 100 game entries per friend:

  1. Should be ready to accept commands within 3 seconds of launch.
  2. Should display friend listing or filtering results within 2 seconds of command submission.

Usability

  1. Users with above-average typing speed for regular English text should be able to add, edit, delete, list and filter friends, and add, delete and list game entries, faster using commands than the mouse.
  2. First-time users should be able to add a friend and a game entry for that friend within 5 minutes of launch, using only the in-app help and sample data.
  3. Invalid commands should explain the error and show the correct usage or allowed input range, without modifying data.
  4. All commands in the User Guide should be usable through the command box alone.

Constraints

  1. Friend names, game names, usernames and metadata are user-provided and are not verified against online gaming platforms.

Glossary

  • Modern computer: A computer with a mainstream OS, 16 GB of RAM, a 512 GB SSD and a mid-range modern processor. Examples of that processor class include Intel Core i5 and AMD Ryzen 5.
  • Mainstream OS: Windows, Linux, Unix or macOS.
  • Friend: A person stored in GameMates with a unique name. Contact details and game entries are optional.
  • User profile: The current user’s separately stored details. Use edit myself ... to edit the profile. Friend-list commands preserve it.
  • Game entry: A record that a friend plays a game. It contains a game name, an in-game username and optional metadata.
  • Role: A job or duty that a friend plays in a game. Examples include Sniper and Healer.
  • Game name: The user-provided name that identifies a game within one friend’s game entries. Aliases such as “Val” and “Valorant” are different game names.
  • In-game username/Handle: The name or alias a friend uses within a game. It can differ from their real name and from their usernames in other games.
  • Metadata: Additional details in a game entry, such as role, preferred weapon, server or play style. Enter metadata with gameadd and m/KEY:VALUE. Replace or clear it with gameedit. Game cards show metadata below the username.
  • Metadata key: The label before the first colon in a metadata item. For example, Role in Role:Sentinel.
  • Metadata value: The information after the first colon in a metadata item. For example, Sentinel in Role:Sentinel.
  • Friend index: A positive number that identifies a friend’s position in the currently displayed friend list.
  • Currently displayed list: The friend list shown after the active filters have been applied. Friend indices refer to this list.
  • Filter: A condition that narrows a displayed list, such as a name keyword or game name.
  • Name keyword: A full word matched against a friend’s name, ignoring case. A substring such as Dav does not match David.
  • Case-insensitive comparison: A comparison that treats uppercase and lowercase letters as equivalent.
  • Trimmed value: A value with its leading and trailing spaces removed.
  • Duplicate: Two entries that the project matching rules consider the same. Both entries are therefore not allowed together.
