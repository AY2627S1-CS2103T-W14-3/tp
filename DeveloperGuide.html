Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app’s work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component’s implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of MainWindow, CommandBox, ResultDisplay, FriendListPanel, FriendDetailsPanel, GameDetailsCard, HelpWindow and StatusBarFooter. These inherit from UiPart, which loads matching FXML layouts. MainWindow.fxml keeps the observable friend list on the left of a SplitPane and the details panel on the right. FriendDetailsPanel renders contact details, tags and sorted game cards; it does not replace the friend list.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Friend objects from the model.

FriendListPanel sends selection changes to a consumer owned by MainWindow. Command-driven selection uses CommandResult.friendToShow and gameFilter, described under Viewing a friend’s games. Successful results without a friend payload show Logic.getMyself(); a single-result find selects that friend. Parse or command failures update feedback without explicitly refreshing details. A game filter is applied only while rendering cards, preserving both the model and the left-hand friend-list predicate.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a GameMatesParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a friend).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The command creates a CommandResult. LogicManager saves the complete ReadOnlyGameMates through Storage before returning it to the UI. Saving applies to viewing commands too. Parse and execution failures skip saving; an I/O error after execution is translated into a CommandException without rolling back the in-memory change.

How the parsing works:

  • When called upon to parse a user command, the GameMatesParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The GameMatesParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Optional values

Command parsers and edit descriptors use Vavr Option to represent omitted values. A missing prefix is absent, while a supplied prefix with an empty value is present and subject to validation. Add commands default omitted contact details to Phone.EMPTY and Email.EMPTY. Edits preserve omitted fields; a single empty t/ clears the tags. Descriptor tag getters expose an unmodifiable set, and setters retain defensive copies.

Parsing continues to report the first invalid value through ParseException. Vavr’s checked-function adapters propagate the original exception, so invalid input is never treated as an omitted argument.

Model component

API : Model.java

The Model component,

  • stores friends in GameMates through UniqueFriendList, plus a separate Friend myself profile with a default value. The profile is not in the friend list. Add/edit commands separately prevent names shared between a friend and the profile.
  • exposes an observable FilteredList<Friend> backed by the stored friends. The filter is a predicate over the full list, rather than a second collection of copied friends.
  • stores each friend’s games as Game objects, including their game name, username and optional metadata.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Friend contains Name, optional contact values, a set of Tag objects and a set of Game objects. Game contains GameName, Username and an immutable metadata set. Name equality ignores case and collapses repeated ASCII spaces; GameName.equals compares complete names using lower-case normalization with Locale.ROOT. Username preserves case. Game.isSameGame compares game names, while full equality also compares usernames and metadata. The set representation alone does not enforce one entry per game name when different usernames are loaded from JSON; do not infer game-command duplicate handling from the proposed specification.

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in GameMates, and each Friend references tags from that list. This lets GameMates maintain one Tag object per unique tag instead of each Friend holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both GameMates data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonGameMatesStorage and JsonUserPrefsStorage (one class per data file).
  • converts game metadata through JsonAdaptedGame and JsonAdaptedMeta, validating fields and rejecting duplicate keys when loading.
  • depends on some classes in the Model component (because the Storage component’s job is to save/retrieve objects that belong to the Model)

Storage reads return Vavr Option: missing files are absent, while malformed JSON or invalid stored friend data still causes DataLoadingException. Vavr Try captures JSON read and model conversion failures, translating captured failures into checked DataLoadingException instances with the original cause. Startup uses sample data for a missing GameMates file and an empty GameMates for a loading error. Missing or unreadable preferences use default preferences. JSON contact fields that are null or empty map to the corresponding empty contact value; invalid nonempty contact values are rejected without trimming. Missing games or tags load as empty sets, and missing myself retains Friend.DEFAULT_MYSELF. Stored games require valid name and username values. Duplicate friend names reject the whole data load, including a previously parsed profile; startup uses a new empty GameMates.

MainApp resolves data/gamemates.json and preferences.json relative to the process working directory, not the JAR’s location. MainApp.initPrefs writes initialized preferences at startup and stop writes them again at shutdown; MainWindow.handleExit first records the current window dimensions and position. The data model is saved by commands, not by stop. Selection and filter predicates are transient.

JsonSerializableGameMates adapts both friends and myself; JsonAdaptedFriend adapts games and tags, and JsonAdaptedGame adapts name, username and metas. Jackson ignores unknown properties, which disappear on the next serialization. Loading a damaged file does not repair or back it up: the next successful command can overwrite it with the fallback data. There is no automatic recovery or atomic transaction spanning command execution and file writing.

Known loading exception: a JSON file containing only the literal null reaches JsonUtil.readJsonFile’s requireNonNull outside its captured conversion, throwing NullPointerException rather than DataLoadingException. It bypasses the normal empty-data fallback and can prevent startup. This needs an application fix separately; the documentation change does not alter the loader.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Friend creation, editing and deletion

AddCommandParser requires n/ and uses Phone.EMPTY and Email.EMPTY for omitted contact values. ParserUtil trims supplied values before calling their model validators. ArgumentMultimap rejects duplicate single-value name/contact prefixes and collects repeated tags into a set. UniqueFriendList rejects names equal under Friend.isSameFriend, so different phone/email values or tags do not distinguish duplicate names.

EditCommandParser requires a numeric index or case-insensitive myself, represented by Index.myself(). An omitted selector is rejected. EditCommand handles the profile selector before accessing a friend-list index, updates Model.setMyself without resetting the friend filter, and returns feedback that displays the profile. Add/edit commands reject names shared between a friend and the profile. EditFriendDescriptor uses optional values to distinguish omission from a supplied empty contact field. EditCommand resolves the index against Model.getFilteredFriendList() and constructs a new friend with the original games. Name/contact values replace existing values. Supplied tags are toggled by set membership; duplicates in one command are deduplicated, and a single empty t/ clears all tags. Empty and non-empty tag parameters together fail validation. After a successful add or friend edit, the model resets the friend-list predicate to show all friends. Editing Myself preserves that predicate, including an empty displayed list.

DeleteCommand uses the same displayed-list indexing but keeps the current predicate. It removes the entire friend and their games immediately; there is no confirmation state. Its out-of-range/empty-list error is the shared generic message, while EditCommand and GameListCommand distinguish empty lists and give a displayed range. ClearCommand replaces the friends with an empty GameMates while copying the existing profile.

The implemented contact rules differ from the submitted draft: names are 1–100 ASCII alphanumeric characters/spaces, phones validate digit counts and grouping, and emails validate ASCII dot-atom/domain syntax with length limits. The User Guide specifies the accepted input for users. No phone, email, game name or username is verified against an external service. GameName and Username trim with String.strip(), count UTF-16 code units with String.length(), require a letter/digit code point and reject ISO control code points. This is not a general Unicode printability test.

Name and game filtering

FindCommand installs NameContainsKeywordsPredicate: any full name word matching any supplied keyword, ignoring case, is sufficient. ListCommand either installs PREDICATE_SHOW_ALL_FRIENDS or GameNameMatchesPredicate, which tests whether any of a friend’s games has the exact GameName. Both operate over all stored friends and replace the previous predicate; they do not intersect filters. find does not parse prefixes and list does not parse n/. The find parser only requires a non-empty keyword list; there is no 255-character keyword validation. No-match queries return successful empty results. Filtering never includes or edits the separate profile.

Viewing a friend’s games

gamelist <FRIEND_INDEX> [g/GAME_NAME] selects a friend for the right-hand details panel without changing the left-hand friend list. The flow is:

  1. GameMatesParser routes gamelist to GameListCommandParser. The parser requires one positional index before at most one g/ filter. It recognizes prefixes at whitespace boundaries so unknown prefixes and repeated g/ tokens cannot silently become part of a multiword game name. Other words after g/ belong to the name. Index parsing uses ParserUtil.parseIndex, and game validation uses the existing GameName rules. Command-specific errors are translated locally, leaving other commands’ validation and messages unchanged.
  2. GameListCommand.execute resolves the index against Model.getFilteredFriendList(), so indices remain correct after both name searches and game-based friend filtering. It checks empty and out-of-range lists before lookup. It uses GameName.equals for exact, case-insensitive matching. No match and no games return successful results.
  3. CommandResult carries the original Friend in friendToShow and an optional GameName in gameFilter. The filter requires a selected friend, participates in equality, hashing and diagnostic output, and defaults to empty in the existing constructors. Feedback uses the stored game name on a match and the trimmed query when there is no match.
  4. MainWindow.refreshFriendDetails forwards both payload fields to FriendDetailsPanel.setFriend. The panel filters the stream used to construct GameDetailsCard instances and displays an explicit empty label if the stream has no entries. It never constructs a replacement friend or modifies the original game set. An unfiltered command clears the game filter. The existing two-argument setFriend also clears it, including when FriendListPanel reports another selection. A single-result find continues selecting the whole friend. Parse and execution failures do not refresh the panel, preserving the previous game display.

The command does not update the model’s friend-list predicate, friends, games, preferences or Myself profile. The existing profile fallback and its rendering are preserved. GameDetailsCard currently renders the available Game.getGameName() and Game.getUsername() fields. Metadata storage has merged, but cards do not yet render Game.getMetas(). Extend the card using Meta.getKey() and Meta.getValue() and add rendering/preservation tests; the command’s original-friend payload already retains metadata without copying or removing it.

Parser and command tests cover errors, exact matching, empty results, displayed-list indexing and unchanged model data. JavaFX panel and window tests exercise filtered payloads, empty states, clearing by commands and selection, and preservation of the details view after invalid input.

Game metadata

Metadata records game-specific details such as a friend’s role or play style. Meta, MetaKey and MetaValue are immutable classes in seedu.address.model.game.meta. Each Meta contains one key and one value. Game copies the supplied metadata collection and exposes it as an unmodifiable set through getMetas(); the two-argument constructor defaults to an empty set.

Validation and equality

Leading and trailing whitespace is removed with String.strip() before validation and storage. StringUtil.isValidTextField() requires non-empty text with at least one letter or digit and no ISO control characters. Limits use String.length() (UTF-16 units), so supplementary characters count as two. This check allows punctuation and does not exclude other Unicode categories, such as format characters. GameName and Username also use this utility.

Field Length after trimming Colon handling Equality
MetaKey 1–50 Colons rejected Case-insensitive using Locale.ROOT
MetaValue 1–200 Colons allowed Case-sensitive

Keys must be unique within each game entry, including when repeated pairs have identical values. The same key can occur in other games or friends. Game enforces this invariant when constructed. Meta.equals() compares both fields; Game.equals() includes metadata, while isSameGame() compares only the game name.

Parsing

ParserUtil.parseMeta() uses StringUtil.splitAtFirstColon() and delegates field parsing to parseMetaKey() and parseMetaValue(). For example, ` Role : Support:Mid ` becomes key Role and value Support:Mid. Missing separators and invalid fields cause ParseException.

parseMetas() parses a collection of raw values and rejects duplicate normalized keys before returning a set. Callers must supply all raw values, without first deduplicating them, so identical repeated pairs are also rejected. These are parser utilities; command-specific metadata flag handling is not yet implemented.

Persistence and testing

JsonAdaptedGame stores metadata as a metas array of JsonAdaptedMeta objects:

{
  "name": "Valorant",
  "username": "player",
  "metas": [{ "key": "Role", "value": "Support:Mid" }]
}

Missing or null metas fields load as an empty set, preserving compatibility with existing save files. Null array entries, invalid fields and duplicate keys cause IllegalValueException during model conversion.

Tests cover trimmed length boundaries, Unicode, control characters, colons, case normalization, duplicate keys, immutability, JSON round-trips and metadata preservation during contact edits. GameBuilder.addMeta("Role", "Support") appends a pair; withMetas(...) replaces the collection. Duplicate keys added through the builder are rejected by build().

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedGameMates. It extends GameMates with an undo/redo history, stored internally as an gameMatesStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedGameMates#commit() — Saves the current GameMates state in its history.
  • VersionedGameMates#undo() — Restores the previous GameMates state from its history.
  • VersionedGameMates#redo() — Restores a previously undone GameMates state from its history.

These operations are exposed in the Model interface as Model#commitGameMates(), Model#undoGameMates() and Model#redoGameMates() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedGameMates will be initialized with the initial GameMates state, and the currentStatePointer pointing to that single GameMates state.

Step 2. The user executes delete 5 command to delete the 5th friend in the GameMates. The delete command calls Model#commitGameMates(), causing the modified state of the GameMates after the delete 5 command executes to be saved in the gameMatesStateList, and the currentStatePointer is shifted to the newly inserted GameMates state.

Step 3. The user executes add n/David …​ to add a new friend. The add command also calls Model#commitGameMates(), causing another modified GameMates state to be saved into the gameMatesStateList.

Note: If a command fails its execution, it will not call Model#commitGameMates(), so the GameMates state will not be saved into the gameMatesStateList.

Step 4. The user now decides that adding the friend was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoGameMates(), which will shift the currentStatePointer once to the left, pointing it to the previous GameMates state, and restores the GameMates to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial GameMates state, then there are no previous GameMates states to restore. The undo command uses Model#canUndoGameMates() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

The redo command does the opposite — it calls Model#redoGameMates(), which shifts the currentStatePointer once to the right, pointing to the previously undone state, and restores the GameMates to that state.

Note: If the currentStatePointer is at index gameMatesStateList.size() - 1, pointing to the latest GameMates state, then there are no undone GameMates states to restore. The redo command uses Model#canRedoGameMates() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.

Step 5. The user then decides to execute the command list. Commands that do not modify the GameMates, such as list, will usually not call Model#commitGameMates(), Model#undoGameMates() or Model#redoGameMates(). Thus, the gameMatesStateList remains unchanged.

Step 6. The user executes clear, which calls Model#commitGameMates(). Since the currentStatePointer is not pointing at the end of the gameMatesStateList, all GameMates states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add n/David …​ command. This is the behavior that most modern desktop applications follow.

Design considerations:

Aspect: How undo & redo execute:

  • Alternative 1 (current choice): Saves the entire GameMates.
    • Pros: Easy to implement.
    • Cons: May have performance issues in terms of memory usage.
  • Alternative 2: Individual command knows how to undo/redo by itself.
    • Pros: Will use less memory (e.g. for delete, just save the friend being deleted).
    • Cons: We must ensure that the implementation of each individual command is correct.

Appendix: Requirements

Product scope

Target user profile:

  • Play multiple online or multiplayer games.
  • Have many gaming friends across different games or platforms.
  • Want to remember each friend’s in-game usernames, preferred roles, servers, play styles, or other game-specific details.
  • Prefer using a command-line interface over navigating menus and mouse interactions.
  • Prefers a desktop application for managing gaming contacts.
  • Is comfortable typing commands to manage information quickly.
  • Still wants a simple visual interface to view their friend and game information clearly.

Value proposition: Manage gaming friends and their game-specific details faster than generic contacts apps, spreadsheets, or chat history searches.

Non-Functional Requirements

The following are targets, not measured guarantees. Targets involving game modification or metadata entry/display remain pending integration; startup/performance and large-data capacity need separate measurement.

Environment

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should work offline on a single user’s personal laptop, without requiring an internet connection or any installed software other than Java 25 or above.
  3. Should work on screens with a resolution of 1280 x 720 or higher, with all panels and the command box visible without scrolling the window at its default size.

Data

  1. All data should be stored locally in a human-editable JSON file. GameMates should not send any data over the network.
  2. Successfully saved data should be restored on the next launch from the same working directory. Current data saves occur after successful commands; window preferences save on shutdown. Metadata persistence is implemented in the JSON adapters.
  3. If the data file is missing, GameMates should start with the sample data without crashing. If the data file is corrupted, GameMates should start with an empty list without crashing.

Capacity

  1. Should be able to hold up to 1000 friends, each with up to 100 game entries.

Performance

  1. GameMates should be ready to accept commands within 3 seconds of starting the application on a modern computer running Java 25, with up to 1000 friends and 100 game entries per friend.
  2. GameMates should display the results of each friend listing or filtering command within 2 seconds of submission on a modern computer running Java 25, with up to 1000 friends and 100 game entries per friend.

Usability

  1. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to add, edit, delete, list and filter friends, and add, delete and list game entries, faster using commands than using the mouse.
  2. A first-time user should be able to add a friend and add a game entry to that friend within 5 minutes of first launching GameMates, using only the in-app help and the sample data as a reference.
  3. Every invalid command should produce an error message that states what was wrong and shows the correct usage or allowed input range, and should not modify any data.
  4. Every command described in the User Guide should be usable through the command box alone, without needing the mouse.

Constraints

  1. GameMates does not verify friend names, game names, usernames or metadata against any online gaming platform. All such data is whatever the user enters.

Glossary

  • Modern computer: A computer running a mainstream OS with 16 GB of RAM, a 512 GB SSD, and a mid-range modern processor such as an Intel Core i5 or AMD Ryzen 5.
  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Friend: A person stored in GameMates, identified by a unique name and optionally associated with contact details and game entries.
  • User profile: The current user’s separately stored details, edited using edit myself ... and preserved by friend-list commands.
  • Game entry: A record that a friend plays a game, containing a game name, in-game username and optional metadata.
  • Role: A job or duty a friend plays as in a particular game, for example a friend can play as a Sniper or a Healer.
  • Game name: The user-provided name used to identify a game within one friend’s game entries. Aliases such as “Val” and “Valorant” are treated as different game names.
  • In-game username/Handle: The name/alias a friend uses within a particular game. It may not refer to their real name and can be different for different games.
  • Metadata: Additional stored information for a game entry, such as a role, preferred weapon, server or play style; command entry and card rendering are not yet supported.
  • Metadata key: The label before the first colon in a metadata item. For example, Role in Role:Sentinel.
  • Metadata value: The information after the first colon in a metadata item. For example, Sentinel in Role:Sentinel.
  • Friend index: A positive number representing a friend’s position in the currently displayed friend list.
  • Currently displayed list: The friend list currently shown after any active filters have been applied. Friend indices refer to this list.
  • Filter: A condition used to narrow a displayed list, such as a name keyword or game name.
  • Name keyword: A full word matched against a friend’s name, ignoring case. A substring such as Dav does not match David.
  • Case-insensitive comparison: A comparison that treats uppercase and lowercase letters as equivalent.
  • Trimmed value: A value after its leading and trailing spaces have been removed.
  • Duplicate: Two entries considered the same according to the project’s matching rules, and therefore not both allowed.

Appendix: Instructions for manual testing

Prerequisites and test isolation

Use JDK 25 and a graphical desktop. Build with ./gradlew shadowJar, then copy build/libs/gamemates.jar into an empty disposable folder. Open a terminal in that folder and run java -jar gamemates.jar. Never use a real user’s data for deletion, corruption or write-failure tests. Use a new disposable folder for each scenario labelled fresh sample data; do not run two app instances against the same data file. Commands below are entered in the application’s command box, not the terminal.

Launch, help and window settings

Prerequisite: fresh sample data.

  1. Launch from the disposable folder. Expected: six sample friends on the left; the right panel says Your details and No details added. A missing data file is not a crash.
  2. Enter help. Expected: feedback Opened help window., a Help window containing the User Guide URL and Copy URL button. Copy and open it in a browser. Close the Help window and press F1 to reopen it.
  3. Resize/move the main window, then enter exit. Relaunch from the same folder. Expected: saved size/position restored, all friends visible, default profile on the right.
